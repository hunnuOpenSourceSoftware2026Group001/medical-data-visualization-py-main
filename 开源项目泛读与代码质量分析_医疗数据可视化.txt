项目名称：基于 Python 的医疗疾病数据分析大屏可视化系统（开源代码泛读与质量分析报告）

一、项目概述（框架与运行形态）
- 后端：Flask 提供 RESTful API，核心入口为 `app.py`，业务计算聚合在 `utils/`、`machine/` 模块；数据库使用 MySQL，基础 SQL 脚本见 `medicalinfo.sql`。
- 前端：Vue 2（`front-end-template-1-master`）+ DataV 组件库 + ECharts/wordcloud，用 Axios 调用后端接口并进行可视化展示；`vue.config.js` 使用开发代理将 `/api` 转发到 Flask 端口。
- 数据流：MySQL → `utils/query.py` 查询 → `utils/getPublicData.py`、`utils/getAllData.py` 聚合统计 → `app.py` 返回 JSON → 前端 Axios 获取 → 通过 ECharts/DataV 渲染图表。

二、项目目录结构（后端为主）
- `app.py`：Flask 路由与接口聚合（`/getHomeData`、`/submitModel`、`/tableData`）。
- `utils/`
  - `query.py`：数据库访问（建立连接并提供 `querys` 方法）。
  - `getPublicData.py`：从数据库读取病例基础数据。
  - `getAllData.py`：对病例数据做统计、聚合，产出可视化所需结构（饼图、环图、词云、折线/柱状等）。
- `machine/`
  - `tree.py`：基于 `jieba`、`scikit-leearn` 的 ML 训练与预测（服务于 `/submitModel`）。
- `medicalinfo.sql`：MySQL 初始化脚本。
- `front-end-template-1-master/`：Vue 前端工程（DataV + ECharts + Axios）。

三、关键代码与注释（节选说明）
1) `app.py`（API 门面与数据编排）
- 作用：统一向前端暴露 REST 接口；内部调用 `utils`/`machine` 的函数完成统计/预测。
- 典型路由：
  - `/getHomeData`：汇总各类统计（年龄分布、病例类型、医院/科室、性别比例、身高体重统计、词云数据等），一次性返回前端所需的全部首页数据，减少多次请求。
  - `/submitModel`：训练模型并对输入文本进行预测。
  - `/tableData`：返回表格数据（去除首列 ID）。

2) `utils/query.py`（数据访问抽象）
- 作用：封装数据库连接与查询执行，向上提供统一的 `querys(sql, params, type)` 接口，屏蔽底层 `PyMySQL` 细节。
- 风险点：当前使用模块级全局连接与游标；未配置连接池与自动重连；数据库配置硬编码。

3) `utils/getAllData.py`（统计逻辑聚合）
- 作用：以病例原始记录为输入，计算：
  - 年龄段占比（饼图），
  - 病例类型 TopN（胶囊图），
  - 医院/科室环形图数据，
  - 性别占比与男女病例类型分布，
  - 身高/体重按疾病类型的均值（折线/柱状），
  - 词云数据（由 `machine` 或公共数据产出）。
- 注意：有打印调试输出与若干魔法数/硬编码区间，可进一步参数化。

4) 前端 `vue.config.js` 与 `src/views/Index.vue`
- 代理：`/api` → `http://localhost:5000`，解决开发态跨域。
- 视图：`Index.vue` 中通过 `this.$http.get("/getHomeData")` 取数，ECharts+DataV 按配置项渲染。

四、项目中可识别的设计模式（结合代码）
1) 门面模式（Facade）
- 场景：`app.py` 作为后端 API 门面，聚合多源数据处理（`utils.getAllData`、`utils.getPublicData`、`machine.tree`）。
- 价值：
  - 对前端只暴露简洁的 REST 接口（如 `/getHomeData` 一次返回所有首页组件所需数据）。
  - 隐藏内部复杂统计与数据整合细节，降低前端耦合度。

2) 仓储/数据访问模式（Repository/DAO）
- 场景：`utils/query.py` 将 SQL 执行封装为 `querys(...)`；`utils/getPublicData.py` 进一步抽象成领域数据获取接口（如 `getAllCasesData()`）。
- 价值：
  - 分离业务统计与存储访问，便于更换数据库或增加缓存层。
  - 使上层统计函数以“读领域对象”心智编程（而不是直接拼 SQL）。

3) 代理模式（Proxy）
- 场景：前端 `vue.config.js` 使用 devServer 代理，将 `/api` 请求代理到后端 Flask（`target: 'http://localhost:5000'`）。
- 价值：
  - 解决跨域与本地开发路由问题，前端以统一路径 `/api` 访问后端。

4) 单例倾向（Singleton-like，全局资源）
- 场景：`utils/query.py` 在模块级创建了全局 `conn`、`cursor`，在整个进程中被复用。
- 价值与风险：
  - 价值：复用连接，避免频繁创建释放。
  - 风险：缺乏连接池与线程隔离，易出现并发/断线问题；更推荐使用连接池或按请求上下文管理连接。

5) MVC/前后端分离的架构风格（非严格模式）
- 场景：前端 Vue 负责 View（展示），后端 Flask 提供 Controller（接口），Model 由数据库表与统计函数共同承担。
- 价值：清晰的关注点分离，团队协作成本低，易于替换前端技术栈或扩展后端服务。

五、代码质量分析
1) 优点
- 分层清晰：数据访问（`utils/query.py`）与统计逻辑（`utils/getAllData.py`）解耦；API 层（`app.py`）职责明确。
- 前端可视化能力强：DataV + ECharts 组合覆盖装饰、图表、动效等多种场景。
- 接口聚合友好：`/getHomeData` 一次返回，减少前端多次请求/等待。

2) 可改进问题
- 数据库配置硬编码：`host/user/password/database/port` 写死在 `utils/query.py`，影响安全性与可迁移性。
- 全局连接与游标：缺少连接池、自动重连、线程隔离；并发场景不安全。
- 输入校验与异常处理不足：接口未对请求体、查询参数、数据库异常进行充分校验/捕获，易出现 500。
- 调试输出与魔法数：`print(...)` 较多（如统计函数中），年龄区间、TopN 值等硬编码，建议以配置或常量表达。
- 可能的逻辑缺陷：年龄段字典存在重复键（`'10-20岁'` 出现两次），应修正；身高/体重为 `'无'` 的处理条件 `if caseItem[10] and caseItem[11] == '无':` 语义不严谨，可能导致类型转换异常。
- SQL 注入与参数化：虽有 `cursor.execute(sql, params)` 基础，但上层需确保所有 SQL 都采用参数化，避免字符串拼接。
- 后端返回结构与前端依赖强耦合：建议为响应结构建立显式的响应模型/Schema，便于演进与兼容。

3) 改进建议（落地措施）
- 配置化与环境隔离：
  - 将数据库配置迁至 `.env` 或 `config.py`，区分开发/测试/生产，使用环境变量加载。
  - 在 `app.py` 中加载配置并注入到 `query` 层。
- 连接管理：
  - 引入连接池（如 `pymysqlpool` 或 SQLAlchemy 的 `create_engine(pool_size=...)`）。
  - 在请求上下文创建/回收连接，或使用 ORM SessionScope（Unit of Work 思路）。
- 错误处理与日志：
  - 使用 `try/except` 捕获数据库与业务异常，返回带错误码/错误信息的 JSON。
  - 使用标准日志库（`logging`）替代 `print`，分级输出到控制台/文件。
- 数据与计算健壮性：
  - 统一校验数据字段类型与缺失值；对 `'无'`、空字符串、`None` 做归一化处理。
  - 将年龄区间、TopN、图表配置项提取为常量或配置文件。
- 接口契约：
  - 为主要接口编写 Swagger/OpenAPI 文档；定义稳定响应模型（字段名、数据类型、含义）。

- 数据路径清晰：从 SQL → 统计聚合 → API → 前端渲染的“流式”链路，便于定位问题与优化瓶颈。
- 可扩展性：

- 适合教学与二次开发：结构直观，利于快速上手与动手实践。
